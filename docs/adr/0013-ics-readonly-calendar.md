# ADR 0013：ICS 只读日历集成

日期：2026-09-17

状态：已接受

## 背景

日历视图里只有 todo，没有日程。用户要知道「今天下午有没有会」得切到另一个日历应用，而「今天要做什么」和「今天被占了多少时间」本来应该一起看。

需求是把外部日历（公司日历、Google Calendar、订阅的课程表）显示在 TextPlan 的日期格里。

## 决策

支持订阅 `.ics` 地址，**只读**展示。

### 只读边界

这是本 ADR 最重要的一条：

- 不创建、不修改、不删除任何外部日历事件
- 不做双向同步，不回写订阅源
- 日程**不写进 vault 的 Markdown 文件**，只在视图里渲染
- 日程不参与 todo 状态切换，也不参与归档

理由：双向同步需要处理认证、冲突解决、离线队列和删除语义，复杂度远超「看一眼今天有什么会」这个需求。而且 TextPlan 的数据模型是「纯文本文件就是真相源」，把外部日历事件写进文件会立刻破坏这个前提 —— 下次订阅源变了，文件里就留下一堆无法对齐的陈旧副本。

### 分层

解析和网络分开：

- `core/ics.ts` —— 纯文本解析，不发请求，可纯函数测试
- `obsidian/icsClient.ts` —— 拉取、缓存、失败降级

用 Obsidian 的 `requestUrl` 而不是 `fetch`：`requestUrl` 走主进程，不受渲染进程 CORS 限制，而日历服务商的订阅地址基本都不带 CORS 头，`fetch` 会直接被浏览器拦掉。

### 解析范围

支持刚好覆盖「只读展示」所需的部分：

- 折行（CRLF + 空格续行）
- 带时刻事件、全天事件（`VALUE=DATE`）、UTC 换算到本地
- 跨天事件（在覆盖的每一天各展开一条）
- `RRULE` 的 DAILY / WEEKLY / MONTHLY / YEARLY 四种基础频率，含 `COUNT` / `UNTIL` / `EXDATE`

不支持的 `RRULE` 部分（`BYSETPOS`、复杂 `BYDAY` 组合等）**降级为只显示起始那一次，不丢弃事件**。少显示几次重复好过整条事件消失。

**全天事件的 `DTEND` 按 RFC 5545 视为排他**：`DTSTART;VALUE=DATE:20260917` + `DTEND;VALUE=DATE:20260920` 是 17、18、19 三天，不含 20 日。带时刻事件的 `DTEND` 是包含性终点，两者算天数的方式不同，由 `getSpanDays(start, end)` 区分。这条规则实现时搞错过一次，会让每个全天跨天事件都多显示一天。

### 规模与失败

- `MAX_OCCURRENCES`（400）和 `MAX_SPAN_DAYS`（60）兜住展开规模，防止「每天重复」的事件撑爆日历
- 只拉取当前显示窗口覆盖的范围，不一次拉整年
- 缓存 TTL 15 分钟，键是 `sourceId | url | 窗口`
- 单个源失败时沿用该源上一次的缓存结果，失败的源名交给 UI 提示 —— 让日历突然空掉比显示旧数据更糟，但也不能静默失败

## 后果

**好处：**

- todo 和日程在同一个格子里，「今天要做什么」和「今天被占了多少」一起看
- 只读边界让实现和风险都可控，不需要认证和冲突解决
- 解析逻辑在 `core/`，可纯函数测试（`tests/ics.test.ts` 9 个用例），未来独立版可直接复用

**代价与风险：**

- 事件占用日期格高度，参与 `+x` 溢出折叠。订阅源多的时候 todo 会被挤掉，靠总开关和单源开关让用户自己控制
- 不支持的 `RRULE` 会少显示重复次数，且**不告诉用户**。这是有意的取舍（提示噪音大于价值），但如果用户报「有些重复会议没显示」，需要先查这里
- 订阅地址明文存在插件设置里。带私密 token 的订阅地址（Google Calendar 的 secret address）会落在 `data.json`，不适合放进公开同步的 vault —— 目前不做加密，属于已知限制
- 拉取失败时显示旧数据，用户可能看到过期日程。缓解措施是提示失败源名，但用户不一定会注意
