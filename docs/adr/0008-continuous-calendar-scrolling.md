# ADR 0008: 连续日历滚动（已废弃）

## 状态

**已废弃**，被 [ADR 0009: 日历分页与窗口占满](0009-paged-calendar-fill-viewport.md)取代。

本 ADR 记录一个被实际使用推翻的决策，保留以说明为什么不再走这个方向。

## 背景

第二迭代初版把月视图和周视图实现为分页：月视图一次渲染一个月，周视图一次渲染一周；滑动超过阈值后整页替换为相邻日期范围。

当时的判断是：分页切换会丢失跨周、跨月的上下文，用户不能停在两个周行之间查看相邻内容；手势阈值、滚轮冷却和格子内滚动也互相干扰。

## 原决策

日历改为浏览器原生的连续垂直滚动条带：周行按时间顺序连续排列，以打开视图时的当前日期为中心预生成前后各一年（约 105 周），用户可以停在任意滚动位置。月/周模式不再是分页单位，只决定周行高度密度与切换后的定位；工具栏标题由 `IntersectionObserver` 跟随视口内占比最大的周行。

## 为什么废弃

上线到真实 vault 后，用户明确要求回到分页形态。原决策的问题：

- **周行必须使用固定行高**（月 92px / 周 220px）才能连续排列，日历因此不再随窗口高度自适应。内容超出面板后出现滚动条，星期列头被压缩换行，整体观感明显差于分页版本。
- **「看到半个格子」不是用户想要的**。用户的实际心理模型是「一屏就是一个月」或「一屏就是一周」，部分可见的周行只造成视觉噪音。
- 原决策认定的收益「保留跨周跨月上下文」，在窗口只有 6 行高度时并不成立——能多看到的半行信息量极小，代价却是整个布局失去自适应能力。
- 手势冲突问题不需要用连续滚动解决：改为按钮翻页后，自定义 touch/wheel 监听同样可以完全不注册。

结论是原 ADR 把「滑动手势不好用」错误地归因到了分页模型上，实际要去掉的是手势，不是分页。
