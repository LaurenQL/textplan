# ADR 0012：跨插件日记文件复用

日期：2026-09-17

状态：已接受

## 背景

用户的 vault 里往往已经有日记文件，来源可能是 Daily Notes 插件、Periodic Notes 插件，或者手工建的。

原来 TextPlan 只按「当前配置的日记目录 + 文件名格式」算出一个路径，文件不在那儿就新建。结果是同一天出现两份日记：一份在 Daily Notes 的目录，一份在 `textplan/`。用户点日历打开的是 TextPlan 那份空文件，而真正写了东西的那份在别处，体验上等于数据丢了。

ADR 0004 已经解决了「读取 Daily Notes 的配置」，但没解决「vault 里已经存在的文件怎么找到」—— 配置读对了，目录换了，历史文件还是找不着。

## 决策

打开某一天时，先在 vault 里找已存在的文件，找不到才新建。

`core/dailyNoteMatch.ts` 的 `matchDailyNote(input)` 按三层顺序查找，先命中先用：

1. **配置目录下的精确路径** —— 按当前生效的目录和格式算出的路径，文件存在就直接用
2. **配置目录下的同名文件** —— 同目录里文件名一致的文件（比较时两边都去掉 `.md`，因为 vault 路径带扩展名而 `formatFileName()` 不带）
3. **其他目录里能反推出同一天的文件** —— 用当前格式串反推 vault 中其他目录下的文件名，解析出同一天就复用

三层都没命中才新建。

**多候选时按路径字母序取第一份**作为主匹配，其余记进 `alternatives`：

- 不静默合并，不删除任何文件 —— 合并和删除都是不可逆的，插件不该替用户做
- 字母序是任意的，但**稳定**。目的不是「选出最对的那份」，而是保证点同一天永远打开同一份文件

反推日期时拒绝不存在的日期（如 `20260230`），否则任何 8 位数字文件名都会被误认成日记。

为什么放在 `core/` 而不是适配层：查找逻辑是纯的字符串和日期计算，输入是路径数组，不需要 `obsidian`。适配层只负责把 `vault.getMarkdownFiles()` 的路径喂进来。

## 后果

**好处：**

- 不再产生重复日记，历史文件能被找到
- 换日记目录或文件名格式后，旧文件仍然可达
- 查找逻辑可纯函数测试（`tests/dailyNoteMatch.test.ts` 10 个用例）

**代价与风险：**

- 第 3 层会扫描 vault 里全部 Markdown 文件。大 vault 上有成本，目前靠「只在点击某一天时查一次」控制，没有做索引
- 接口必须同时传 `formatFileName`（格式化函数）和 `fileNameFormat`（原始格式串）。这个冗余不好看，但第 3 层要的是 `parseDateFromFileName(格式串, 文件名)`，传格式化后的结果（`"20260917"`）会因为串里没有 `YYYY`/`MM`/`DD` token 而永远返回 `null` —— 实现时确实踩过这个坑
- 字母序选主文件对用户不可见也不可配。如果将来有用户抱怨「为什么打开的是 archive 那份」，再考虑加偏好目录设置
